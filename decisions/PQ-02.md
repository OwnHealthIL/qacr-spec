**The question.** At milestone 3, is anything owed client-side for the one-time password attempt
limit, given that the requirement defining the limit arrives at milestone 4?

**What makes it a question.** FR-AUT-018 is at **M3** and requires each resend request to count
against the attempt limit of FR-AUT-005 — which is at **M4**. Read literally, M3 ships a resend
interval that counts against a limit no requirement has yet put in force.

FR-AUT-005's note states the values are set by the backend SRS and **enforced server-side**, which
suggests the client counts nothing and there is no gap at all: at both milestones the client
presents what the backend returns. The brief's milestone line is consistent with that, placing "the
OTP attempt limits" at 4 deliberately. But the reading has not been stated, and the alternative —
that the client maintains its own count — produces a different M3 deliverable.

**What happens if nobody answers.** The likely default is the correct one, and nothing is built
wrongly. The risk is the reverse: a developer reading FR-AUT-018 literally implements a client-side
counter that duplicates a server-side control, and the duplicate then disagrees with the backend at
the boundary — a lockout the client believes in and the server does not, or the reverse.

One sentence from Product closes it: whether the client holds any attempt state at all.
