# What the results centre contains

## The question

Two bits, both about what the results centre is allowed to show:

1. Do **invalidated** tests appear in the results centre?
2. Where more than one user is registered against the same phone number, is a household
   **intended** to see one another's results, or is each user's view strictly their own?

## What makes it a question

`FR-PRT-001` (milestone 3) does not leave this to inference — it says so itself. The requirement
text is:

> The software shall provide a results center as a screen of its own, giving the authenticated user
> ongoing access to their most recent result and stating the date on which that test was performed.
> The backend shall transmit that result on request.

and its note:

> Split at review: the results center main screen shows the most recent result and is milestone 3;
> the history of earlier results is a separate screen and is deferred as FR-PRT-015. **Whether
> invalidated tests appear, and whether results belonging to another registered user on the same
> phone number are excluded, are to be specified;** the second bears on RA 6.4

"Are to be specified" is the whole reason this file exists. Neither half can be answered by reading
the requirement more carefully, because the requirement says it has not been written yet.

**On the first half.** `FR-ALG-012` (milestone 2) requires the result payload to carry "a reason
category for each invalid test, drawn from a defined enumeration, sufficient for the application to
inform the user of the corrective action required." So the backend has the reason and could show it.
The question is whether an invalidated test is a *result the patient has ongoing access to*, or an
event that produced no result. The two readings give different screens, and `FR-PRT-015`'s
"last five results" inherits whichever is chosen.

**On the second half.** The household case is real and dated. `FR-AUT-011` (milestone 5) —
"The software shall permit more than one user to be associated with the same phone number, each
uniquely identified by their Date of Birth." The inherited user-management schema already permits
it: `Users.phone` is nullable and not unique, so nothing has to change for it to become possible.
`FR-AUT-015` adds a switch-user function and `FR-AUT-020` blocks a second test on a shared number
until the user switches — both milestone 5. Those three read as though the users on a shared handset
are distinct subjects who take turns, which is evidence for strict per-user scoping but is not the
same as Product stating it.

## What happens if nobody answers

Architecture has already taken the safe half so that the default is not silently wrong. AD-23 in
`architecture/spine.md` fixes that a patient-facing read is scoped by the **resolved patient
identifier only**, and that the phone number is never a scope, a query key or a lookup path. So the
default that ships is **strict per-user scoping**, and it does not drift when `FR-AUT-011` lands.

Two consequences of that being the default:

- If Product wants household visibility, it is a **new rule** — an explicit, partner-configured
  opt-in — and not a relaxation of AD-23. It costs more to add later than it would have cost to
  design in now, and it is the failure class `FR-SHR-001` exists to prevent (a result reaching the
  wrong person), arrived at inside one partner rather than across two.
- The invalidated-test half has **no safe default**. Architecture cannot pick it, because both
  readings are defensible and the choice is clinical-communication, not structure. Unanswered, it
  gets decided by whoever writes the query.
