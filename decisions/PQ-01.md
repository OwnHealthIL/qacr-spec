**The question.** Does the current product persist an authentication credential, and if it does,
is removing it a departure SPEC-02 owes?

**What makes it a question.** FR-SEC-008 is new from the threat analysis, and its note records the
control as "server-side authentication with **persistent authentication removed**". The brief
dispositions F02.5 `as-is`, which asserts the current product already satisfies the requirement and
there is nothing to design. Those two readings cannot both hold: a control described as *removed* is
either a description of a state the product is already in, or a change to it.

No evidence row exists either way. `evidence/coverage.tsv` records FR-SEC-008 as
`no-evidence-found`, so nothing in this repository establishes what the shipping application does
with credentials at rest, and neither reading can be checked from here.

**What happens if nobody answers.** Two platforms recreate F02.5 from their own reading of the ACR
source, and each decides independently whether persisted credentials are in scope. If the product
does persist one, an undeclared departure is built by inference — and it is a security control
carrying SPTA 1.5, which is the wrong class of requirement to settle at a developer's desk.

Settling the input is one source read against `iosDip` and `AndroidDip`. Settling the question is
Product's: only Product can add the departure row if one is owed.
