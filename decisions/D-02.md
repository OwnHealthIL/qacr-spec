# Screenshot prevention versus saving the results letter to the phone

## The question

Two requirements in the same document require opposite things. Which one changes?

## What makes it a question

`FR-SEC-007` (milestone 3):

> The software shall prevent the user from taking a screenshot of any screen containing personal,
> health or result information, and shall obscure such content when the application is backgrounded
> or when the operating system captures a preview of it, so that it is not exposed in the
> application switcher.

Its note raises the cost of getting this wrong:

> Screenshot prevention added from the threat analysis. **This is the sole control for SPTA 4.14,
> gross score 12**

`FR-SHR-015` (milestone 5):

> The software shall allow the generation of a results letter in PDF format, and shall allow the user
> to save it to the smartphone and share it by email.

and `FR-PRT-009` (milestone 5): "The results center shall enable the user to view the results
letter."

One requirement says result information must never be capturable off-screen; the other saves a PDF
of exactly that information into shared device storage that every application on the phone can read.
The security analysis states it plainly: *"These directly contradict each other: one says results
must never be capturable, the other saves results to a folder every app on the phone can read. One
of the two has to change."*

This is not a milestone accident that resolves itself. `FR-SEC-007` is M3 and `FR-SHR-015` is M5, so
the contradiction arrives when the letter arrives, and by then `FR-SEC-007` will have been verified
and traced as the sole mitigation for a scored threat.

## Why architecture raised it rather than absorbing it

The control is device-side and out of the backend spine's scope. But the resolution can reach the
backend, so it cannot simply be handed back:

- The results letter is **generated backend-side** at M5 — `FR-SHR-015`'s note records that "the
  backend SRS requires letter generation and transmission as SRS-BE COM.10". If the answer is that
  the letter may be saved, QACR owns its generation and its transport, and the spine's `OQ-17` picks
  up what that implies.
- If the answer is that `FR-SEC-007` wins, then something has to serve the patient's legitimate need
  to give a result to a doctor. An emailed letter sent **from the backend** to an address the patient
  supplies never lands in device storage at all, which would keep both requirements intact — but that
  is a different product behaviour from the one `FR-SHR-015` describes, and it is Product's to
  specify, not architecture's to substitute.

## What happens if nobody answers

`FR-SEC-007` is built at M3 as written, because it is the sole control for a scored threat and
nothing justifies weakening it on speculation. Then at M5, whoever implements `FR-SHR-015` finds it
cannot be implemented as written on a build that blocks capture, and the contradiction is resolved at
a developer's desk, under schedule pressure, in whichever direction is easier to code — which is the
expensive place to find it, and the one place where a scored risk control can be narrowed with no
risk file update.
