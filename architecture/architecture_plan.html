Part one

1 · Backend architecture

A modular monolith with ports-and-adapters at the edges (AD-1). One repository, one application image plus a separate algorithm image, many runtime roles — where a role is a Helm alias over the same image, not a service with its own repository. Everything crossing the process boundary is an adapter behind a port.

1.1 Repositories ≈ ACR

One new repository — qacr-backend — and one rename: backend.q-acr becomes qacr-research. The naming convention is the 2026 cohort's: lowercase kebab-case <product>-<role>, no dots. The dot-namespaced form (backend.q-acr, urine.com.services.backend) is the abandoned generation and is not extended.

The boundary rule is mechanical, not cultural (AD-1). CI fails a pull request that imports across workspaces outside the declared graph — the domain may import a port and never an adapter, and no runtime role may import another runtime role. That single rule is what keeps "modular" true after two years, and it is the whole price paid for leaving extraction available later. It is a blocking gate under AD-24.

The management plane — "backdoors to maintain the product without external exposure"

backoffice-api and worker-api are the whole answer, and AD-17 fixes the constraint: operational and callback routes are not reachable from the internet, and every privileged read of patient data emits an FR-SEC-013 audit event identifying the operator. Namespace isolation is backed by NetworkPolicy — a namespace without one is a label, not a boundary. What is not fixed is how staff reach that plane: VPN, identity-aware proxy, bastion, or cluster-internal only. That is OQ-5, and it carries the break-glass procedure and its review cadence with it.

No route anywhere is protected by a shared static credential. The milestone-1 demonstration is the single bounded exception and it is governed by AD-21 — a credential that carries its own expiry, at most 90 days, refused by every M3 route, with CI failing the build if the M1 path survives once AD-6 authentication is enabled.

Open questions this section depends on
  • OQ-5 — the management-plane access mechanism, who holds access, and the break-glass procedure and its review cadence. AD-17 fixes the constraint, not the mechanism. Owner: backend owner + DevOps.
  • OQ-8 — user-management writes patient phone numbers to its application logs, and its OTP path contains a whitelist that bypasses sending. Both are inherited exposures under AD-6 and AD-8. Either a change in user-management, or a documented acceptance with a named owner. Owner: backend owner + user-management owner.
  • PQ-1 — copy user-management and notifications-worker into QACR, or consume them unchanged? The OZ-3 comment (log L12.7) says "we will copy them"; the spine records this as Deferred and consumes both unchanged, because that works today and the costs of consuming are compliance-surface costs rather than capability gaps. The spine's stated ceiling is M5 — reversibility decays with patient volume. This needs settling as a decision rather than left as two documents disagreeing. Owner: backend owner + QMS.
  • PQ-6 — identity-provider due diligence: user-management's per-user-keypair JWT is a nonstandard construction, and its token revocation, rotation and audit story needs verifying against this product's regulatory bar. Reuse remains the right call; the verification is a precondition, not a formality. Owner: backend owner.

1.3 Main user flows

Four flows: app initialization, saving an exam, completion of the analysis, and reporting. The rule that shapes all of them — nothing commercial and nothing secondary sits in the patient's latency budget (AD-16). ≠ ACR ACR's /init calls the prescription and kit-fulfilment services synchronously; that is how commercial concerns entered the clinical latency budget.

1.4 The app-facing contract surface

One artefact carries the contract: contracts/openapi.yaml in qacr-backend, owned by client-api, versioned, with both applications consuming generated clients from it rather than hand-written models (AD-12). What follows is the surface — which operations exist, who may call them, and what binds each. Paths, payloads, status codes and error bodies are the OpenAPI document's and are deliberately not restated: a second copy of a contract is a second contract.

The application talks to two hosts, not one. Identity — phone entry, OTP, session token, PIN — is user-management at accounts-{staging,production}.healthy.io, and qacr-backend implements none of it (AD-6). 2.3 Branching strategy — gitflow ≈ ACR

Two long-lived branches — develop for integration, main for what is in production — with feature/* off develop, release/vX.Y cut from develop per version, and hotfix/* off main. What gitflow costs here, chosen with open eyes

Two long-lived branches mean every fix that matters in production lands twice — once on main, once back on develop — and the drift between them stays invisible until a release goes wrong. Note also that the estate's newer backends (behealthy, the commercial backend, qacr-research) left gitflow for trunk-based with a shared release tool, so QACR will not share their release tooling or cadence — @ownhealthil/release is not used. Gitflow still runs in rehealthy-core and bespot, so it is not foreign to the estate. The regulatory requirements are indifferent to which flow is used; they care only that the tested digest and the shipped digest are the same object, which is why the build sits on the release branch and nowhere else.

3 · Data model

One PostgreSQL schema. Mutable lifecycle state on the exam row; everything that constitutes the record is either an immutable row the exam points at or an append-only child table. Two grafts onto that core: the append-only event log, and one versioned JSONB diagnostics document validated at the write boundary. Full inventory and the alternatives that were rejected are in architecture/data_model.md.

3 The schema, grouped

Milestone growth is additive throughout

  • M1 — demo: partner, config_set, exam, exam_event, exam_frame, exam_trace and nothing else. No patient, no session, no kit register. The result is the fixed FR-RES-006 payload and no outbox row is written, so nothing can leave (AD-20).
  • M2 — usability: algorithm_version, algorithm_approval, exam_result.
  • M3 — submission: patient, auth_challenge, session, kit, content_set, provider_integration, provider_delivery_attempt, system_parameter. Tenancy RLS switched on.
  • M4 — high priority: pin_credential, results_centre_session, invite_code, audit_event — the FR-SEC-013 channel, with a role that cannot read patient tables.
  • M5 — future: consent_ack, results_letter, device_install, plus relaxing patient to N-per-phone-number. Because the phone number is not a query key on any read path, that relaxation is additive and no read changes with it.

What is deliberately absent ≠ ACR

  • No order table and no order_id column. Order arrives later and will reference the exam and kit outward, so no commercial field sits in the clinical record and an exam is valid with no order in existence. The incumbent contract is order-centric throughout.
  • No per-service databases. The roles are processes of one deployable; one database with RLS is one enforcement point for the control that stops a result reaching the wrong provider. A control enforced twice is two controls to get wrong.
  • No second store. Payload variability is absorbed by versioned JSONB columns, not by a document database beside the relational one.
  • Not behealthy's Postgres. cc-api reads and writes it directly and the commercial backend reaches back into it through four hardcoded clients across 26 values files. That fusion is why the ACR core is expensive to change.
  • Commercial seams are named nullable reference columns only — external_payment_ref, fulfillment_ref, prescription_ref. No tables, no state machines, no flows.

On "save all PII in a dedicated table"

The OZ-2 instruction (log L12.7) and the spine's AD-8 want the same outcome by slightly different means, and the difference is worth being explicit about. The model already confines PII to one group of tables — patient holds the identifying attributes and every other table references it by key, so there is one place to answer "where is personal data" and one place to change when retention or erasure is exercised.

What AD-8 adds is that the enumeration itself is an artefact: a register in the repository naming each table and column, updated in the same change that adds one. That is stronger than a naming convention and weaker than forcing every attribute into a single physical table — which would break the foreign keys the clinical record depends on and put the identity row in the same blast radius as the exam row. If a single physical PII table is wanted as a hard requirement rather than a goal, say so and it becomes a schema constraint; otherwise the register plus the confined identity group is what gets built.

The failure this prevents is specific: personal data spreading until nobody can answer where it is — the condition that makes retention, erasure and disclosure assessment unanswerable.

  • Cloud SQL on a private IP only, no public endpoint, egress through the VPC. Point-in-time recovery enabled, with the restore rehearsed rather than assumed.

  • TLS 1.2+ with an explicitly set modern cipher policy, and a CI check that asserts the policy rather than trusting the default (FR-COM-001).

4.1 Error handling and recovery

One error envelope, generic messages, and every state-changing route either provably idempotent or carrying single-use replay protection — stated per route in the OpenAPI document and never left unstated (AD-23).

What a client sees

  • One error envelope across every route. Messages returned to a client are generic and carry no internal detail — no stack trace, class, method, endpoint or version (FR-SEC-004, FR-SEC-010).
  • A digest mismatch, a schema violation or a missing entitlement is a rejection before anything is stored (FR-COM-005, FR-SEC-011).
  • 409 on a frame upload means "already held" and is success — the retry path for a home user's connection.
  • An invalid result is always a reason category from the one server-side versioned enumeration, never a number. Clients map from it and never extend it.

What happens inside

  • The event row is written in the same transaction as the state change, and the relay publishes from the table (AD-9). No handler publishes inline: no events lost when a process dies after committing, no ghost events published before a rollback.
  • Exam creation converges: a retry with the same idempotency key returns the same exam (AD-3).
  • The algorithm callback is the one route that fails the idempotency test, so it carries a single-use credential bound to that exam and that run, accepted at most once (AD-23).
  • Provider retry is the append-only provider_delivery_attempt table plus a queue — never in-process backoff — which makes "what did we send this provider, and when" a query rather than an investigation.
  • Every outbound third-party call records the provider's own correlation identifier and its terminal status as a row, never a log line (AD-15). Given that personal data is correctly absent from logs, this is the only thing that keeps a whole class of support question answerable.
  • A poison message that exhausts retry reaches the DLQ, and dlq-worker archives it and raises an exam-level failure the patient flow can act on.
One retry policy is inherited and has never been established

handleEvent logs "sending to DLQ" and rethrows; the actual requeue count and backoff live inside @ownhealthil/messenger and are read nowhere in QACR code. FR-RDY-012 and FR-COM-006 both retry, so this is on the correctness path — establish and document the policy before relying on it. The same applies to USE_QUORUM_QUEUES, which is read in code and set in neither values file while every queue is named *_quorum: either set it or rename the queues, but do not design on a name.

Recovery — the record's durability is directional

No synchronised recovery point across the database and object storage exists, and none is claimed (AD-26). The guarantee is directional instead, and it is what stops the two stores being configured as independent pieces of work that restore to two different points:

  • A row referencing an object is written only after that object is durably stored, so the database is always behind or equal to object storage and never ahead. The alternative produces exam rows referencing frames that do not exist — which AD-4 forbids repairing with an update.
  • An object is never deleted while a live row references it.
  • There is no bucket-wide rollback: recovery from object loss is a per-object version restore. Object versioning and soft delete are on for every record-bearing bucket.
  • No lifecycle rule deletes a record-bearing object on age alone. A purge is one joint operation across both stores.
  • One stated RPO and one stated RTO bind both stores together, and a restore rehearsal is a periodic, evidenced activity under FR-LCM-010, run in the ephemeral restore-verification environment inside the production deployment.
Open questions this section depends on

AD-26 fixes the shape and the direction; no figure is invented here. The tolerance input is sharp: AD-5 consumes the kit in the same transaction as the exam write, so data lost after commit is a spent kit plus a record AD-4 forbids repairing — the patient needs a new physical kit, and the result cannot be reconstructed for FR-ALG-004.
