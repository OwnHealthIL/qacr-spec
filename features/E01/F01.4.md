## iOS task

Build one ordered, typed decision function on the start tap, in the shape of canStartTest(), that runs the pre-test checks in a fixed order and returns a typed outcome naming the check that refused. Call it from mainButtonTapped() and secondaryButtonTapped() in place of the direct navigator.push, and route each typed failure to its blocking state.

Inside it:

- **Storage** — a free-space check that refuses the start when free space is below the threshold and also refuses when the query itself throws, routing to the storage block.
- **Battery** — a level-only check (departure D1): a device below the minimum level is blocked whether or not it is charging. When the level cannot be read at all, the check passes and the test proceeds.
- **Camera** — carry the authorization state and a requester closure into the instructions chat, as TestCoordinator does; branch granted and denied, and present the denial route on denied. Put the authorization wrapping behind a provider exposing isAuthorized(for:), didDenyAuthorization(for:) — true for .denied and .restricted — and requestAuthorization(for:completion:), and add an authorization check plus a denied branch ahead of cameraManager.start. Replace the placeholder camera usage description with the real string from the content set.
- A camera that fails to start blocks the flow; the user cannot proceed.

Thresholds come from U1. Until they land, read them from configuration rather than fixing them in code.

For FR-RDY-005 and FR-RDY-006, establish and cite the current iOS behaviour first, then build to it.

## Android task

Build one ordered, typed decision function on the start tap, in the shape of requestFlowStart(), that runs the pre-test checks in a fixed order and returns a typed error naming the check that refused. Call it from both start entry points in MainScaffold, keeping the existing permission launcher, the denial dialog and its ACTION_APPLICATION_DETAILS_SETTINGS deep link as the camera branch's route, and route every other typed error to its blocking state.

Inside it:

- **Storage** — a free-space check that refuses the start when free space is below the threshold and also refuses when the query throws, in the shape of IsDiskFullUseCase; drive it from the declared lowDiskSpaceSize, which is currently neither written nor read.
- **Battery** — a level-only check (departure D1): a device below the minimum level is blocked whether or not it is charging. When the level cannot be read at all, the check passes and the test proceeds.
- **Camera** — keep hasCameraPermission() as the permission condition, and run the runtime camera check alongside it. A camera that fails to start blocks the flow; the user cannot proceed.
- Set the manifest camera feature declaration to match the cited baseline for a device that must have a usable camera.

Thresholds come from U1. Until they land, read them from configuration rather than fixing them in code.

For FR-RDY-005 and FR-RDY-006, establish and cite the current Android behaviour first, then build to it.

## Acceptance criteria

1. **automatable** — The start tap calls one ordered decision function; no start entry point reaches the test flow without it (FR-RDY-010).
2. **automatable** — Each refusing check returns a distinct typed outcome, and each typed outcome routes to its own blocking state (FR-RDY-010).
3. **automatable** — With free space below the threshold, the start is refused and the storage block is presented (FR-RDY-008).
4. **automatable** — When the free-space query throws, the start is refused and the storage block is presented (FR-RDY-008).
5. **automatable** — With battery below the minimum level and the device charging, the start is refused (FR-RDY-007, departure D1).
6. **automatable** — With battery below the minimum level and the device not charging, the start is refused (FR-RDY-007, departure D1).
7. **automatable** — When the battery level cannot be read, the battery check passes and the test proceeds (FR-RDY-007).
8. **automatable** — With camera permission not granted, the start requests authorization; granted continues the flow and denied presents the denial route with its settings deep link (FR-RDY-009).
9. **automatable** — With camera permission permanently denied or restricted, the start does not reach the camera and the denial route is presented (FR-RDY-009).
10. **automatable** — When the camera fails to start, the flow is blocked and offers no way to continue (FR-RDY-009).
11. **manual** — On a physical device, the camera permission prompt shows the real usage description from the content set. Requires a first-run install on hardware.
12. **manual** — FR-RDY-005 and FR-RDY-006 behave as the current product does, against the baseline established and cited in the platform task. Requires side-by-side observation of the shipped product.
