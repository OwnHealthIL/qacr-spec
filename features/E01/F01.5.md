## iOS task

Give the readiness blocked states one typed family and one wiring site, in the shape of the contiguous readiness cases and the block configured in a single place. Each state declares its buttons and the block attached to each button; a state with a support route attaches it to the button that carries it, and a state without one presents a single dismissal.

Carry the declared action through BlockFlowCustomAlertDataHandler instead of discarding it, so the .support action on BlockFlowCustomAlertConfig reaches the presented alert and opens support. Configure the block screens so the states that carry support get it — RootedDevice, ServerError and FatalServerError — and NoNetworkConnection and InvalidAppVersion carry none. Where a state has no second button, the second route stays unreachable by construction.

For FR-RDY-013 and FR-RDY-014, establish and cite the current iOS behaviour first, then build to it.

## Android task

Add an action type to AppAlert so a blocked state can carry a route as well as text, then build one route table mapping each blocked state to its action, in the shape of the existing blocked-user route table: RootedDevice, ServerError and FatalServerError carry a support action; NoNetworkConnection and InvalidAppVersion carry none. Presenting a blocked state goes through that table and nothing else.

Bring the camera-permission dialog onto the same path and source its strings from the content set rather than hardcoding them.

For FR-RDY-013 and FR-RDY-014, establish and cite the current Android behaviour first, then build to it.

## Acceptance criteria

1. **automatable** — Every readiness blocked state is presented through the single blocked-state path; no readiness block is presented by an ad-hoc dialog (FR-RDY-011).
2. **automatable** — Each blocked state resolves to exactly one entry in the route table, and every declared state has an entry (FR-RDY-011).
3. **automatable** — A blocked state configured with a support action presents that route, and taking it opens support and emits its analytics event (FR-SUP-003).
4. **automatable** — A blocked state configured without a support action presents a single dismissal and exposes no support route (FR-SUP-003).
5. **automatable** — An action declared on a blocked-state configuration survives the bridge into the presented alert and is invoked when its button is taken (FR-SUP-003).
6. **automatable** — Dismissing a blocked state returns the user to the point it was raised from and does not start a test (FR-RDY-011).
7. **manual** — FR-RDY-013 and FR-RDY-014 behave as the current product does, against the baseline established and cited in the platform task. Requires side-by-side observation of the shipped product.
