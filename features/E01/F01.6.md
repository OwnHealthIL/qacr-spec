## iOS task

Establish and cite the current iOS deferred-upload behaviour before building: where an unsent result is held between launches, what start-up does with it, when the retry runs, what happens when the retry fails again, and when the stored item is cleared. Record that as the baseline, then build recovery at start-up to match it, silently — nothing is shown to the user while a previous result is still uploading.

## Android task

Establish and cite the current Android deferred-upload behaviour before building: where an unsent result is held between launches, what start-up does with it, when the retry runs, what happens when the retry fails again, and when the stored item is cleared. Record that as the baseline, then build recovery at start-up to match it, silently — nothing is shown to the user while a previous result is still uploading.

## Acceptance criteria

1. **automatable** — With a result left unsent by a previous session, start-up picks it up and attempts to send it (FR-RDY-012).
2. **automatable** — While a previous result is still uploading, no notice, banner, dialog or blocking state is presented (FR-RDY-012).
3. **automatable** — A recovered result that sends successfully is cleared from local storage and is not sent again on the next start-up (FR-RDY-012).
4. **automatable** — A recovered result whose send fails is retained and retried on the next start-up (FR-RDY-012).
5. **manual** — Recovery behaves as the current product does across a real launch cycle with connectivity restored mid-flight, against the baseline established and cited in the platform task. Requires observation on hardware with a controlled network.
