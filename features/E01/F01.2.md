## iOS task

Send the device OS version with the init request as platform info, take the backend's OS verdict, and present the blocking OS state on the start path, interpolating the device's own version into the copy the content set supplies. Keep the persisted settings struct as the home for server-supplied values and extend it to carry whatever the supported-device policy needs.

For hardware eligibility (FR-RDY-002) and for FR-RDY-004, establish and cite the current iOS behaviour first, then build to it.

## Android task

Populate supportedHardwareConfig into pre-scan flow state from the init response — the scaffold type and the state field already exist — and pass it into CameraSelectorProvider in place of the null config, so the three config-driven filters (Aperture, SensorResolution, SensorPhysicalSize) apply on top of the three unconditional defaults. Wire the start path to call provideValidator().hasSupportedCamera() and refuse the start with the unsupported-camera outcome when nothing survives the filters.

Give blockFlow a dispatch site and a reducer case so the INVALID_OS_VERSION constant reaches the user as a blocking state on the start path.

For FR-RDY-004, establish and cite the current Android behaviour first, then build to it.

## Acceptance criteria

1. **automatable** — With a supported-hardware configuration supplied by the init response, the app holds that configuration in pre-scan state and each of its fields reaches the camera selector (FR-PLT-005).
2. **automatable** — With a stubbed camera set in which no camera satisfies the configured filters, the start action is refused with the unsupported-camera outcome and no test begins (FR-RDY-002).
3. **automatable** — With a stubbed camera set in which at least one camera satisfies the filters, the hardware condition passes and does not refuse the start (FR-RDY-002).
4. **manual** — On a physical device whose camera fails the configured filters, the user is blocked from starting. Requires hardware that fails the filters, which no simulator reproduces.
5. **automatable** — The init request body carries the device OS version taken from the platform's own reported system version (FR-RDY-003).
6. **automatable** — When the backend returns the invalid-OS verdict, the start is blocked and the OS block state is presented with the device's version interpolated into it (FR-RDY-003).
7. **manual** — FR-RDY-004 behaves as the current product does, against the baseline established and cited in the platform task. Requires side-by-side observation of the shipped product.
