## iOS task

Establish and cite the current iOS device-integrity behaviour before building: what the check is, when in start-up it runs, what it does to the session and to stored data on detection, and what the user meets afterwards. Record that as the baseline, then build the check, the resulting blocked state and its route to match it.

## Android task

Run the integrity check at application start-up and dispatch Actions.DeviceNotTrustworthy on detection — the action and its DeviceReducer case already exist — so DeviceState.isTrustedDevice reflects the result and is read by the code that decides whether the user may proceed. Apply the same session and stored-data handling on detection that the start-up check performs today.

Route the untrusted state to a blocked screen carrying the support action, in the shape of the existing blocked-user route table. Keep the security use-case results flowing through ClientInfoProvider into analytics and request metadata, and carry the blockType analytics string for the untrusted-device state.

## Acceptance criteria

1. **automatable** — With the integrity check reporting a compromised device, the untrusted-device state is dispatched and held in device state (FR-RDY-001).
2. **automatable** — With the integrity check reporting a compromised device, the user is signed out, stored data is wiped, and the user cannot reach the test flow (FR-RDY-001).
3. **automatable** — With the integrity check reporting a clean device, start-up proceeds and nothing is presented (FR-RDY-001).
4. **automatable** — The untrusted-device blocked state offers the support action, and taking it sends the analytics event and opens support (FR-RDY-001).
5. **manual** — On a genuinely rooted or jailbroken handset, the check fires and the block is presented. Requires a compromised physical device, which no emulator reproduces faithfully.
